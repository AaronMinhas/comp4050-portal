# API

The Portal API is a FastAPI application. When it is running, interactive OpenAPI documentation is available at `/docs` (for example `http://127.0.0.1:8000/docs`). This page records the access rules and behaviour that the generated schema does not make obvious. It does not repeat the request and response schemas.

Field names in request and response bodies are PascalCase, for example `ItemCode` and `OrderId`.

## Authentication

Every route except `/health`, `/docs` and the FitVisualiser handoff read requires a Supabase access token:

```text
Authorization: Bearer <access token>
```

| Status | Meaning |
|---|---|
| `401` | Missing, invalid or expired token |
| `403` | The identity has no Portal account, the account is disabled, or the role is not permitted |
| `404` | Order, box type or account not found |
| `409` | The request conflicts with current state, for example an order on hold or an invalid lifecycle transition |
| `422` | Validation failure, including item weight limits and Solver request rejection |

Roles are User, Supervisor and Administrator. In the tables below, **Manager** means Supervisor or Administrator. See [Architecture](architecture.md#authentication-and-authorisation) for how tokens and roles are verified.

## Order Lifecycle

Order IDs are generated by the Portal API in the `ORD-###` format.

Orders have three views: Active orders, On hold (the backlog) and Archive. `GET /orders` returns the active view by default. All signed-in users can read every view and its saved packing results.

### Rejected orders

Order responses include `RejectedCount`, derived from the active saved solution. An optimised order with any rejected items displays as **Rejected** in red in the order list and detail page. It can be edited or re-optimised, and cannot be finalised until all items are packed. The persisted lifecycle status remains `OPTIMISED`; a later successful re-optimisation clears the rejection indicator.

### Optimisation

- `POST /orders/{id}/solve` is available to Managers. Regular Users submit drafts with `/submit` for a Manager to optimise.
- It requires at least one active box with available quantity, and validates item weights against the box capacity.
- A successful optimisation saves the solution and marks the order `OPTIMISED` in one transaction. A failed optimisation leaves the previous state unchanged.
- Results are discarded if the order's items change while the Solver is running, so a stale result cannot be saved against edited items. The backend locks the order before checking state, and rejects stale results when work is paused or deleted.
- Editing an order's items returns it to `DRAFT` and discards its saved solution.

### Hold, resume and delete

- Unfinished orders can be put on hold in the backlog. `HeldAt` records the pause independently of lifecycle status, preserving items, results and progress.
- Resume returns the order to Active at the same stage.
- Orders on hold cannot be edited, submitted, optimised or finalised until resumed.
- An unfinished order can be permanently deleted directly from Active or Backlog. There is no requirement to archive or pause it first. Finalised orders cannot be deleted.
- Hold, resume, archive and deletion never change box stock. Deletion atomically removes only that order's items and saved solution through existing foreign keys.

### Finalisation and archiving

- Finalisation records `FinalisedAt` in the same transaction that consumes stock. It requires an `OPTIMISED` order with no rejected items.
- Finalised orders are automatically archived one calendar month after finalisation, including month-end and leap-year rollover. The backend checks at startup and every minute thereafter, independently of any browser session, and retries failed checks. Startup catches up after server downtime.
- Managers can archive earlier with `/archive`. Archived finalised orders remain readable and retain their items and packing results. They cannot be resumed or deleted.

## Validation

- `ItemCode` is the client's own identifier, limited to 32 characters. `ItemReference` is limited to 100 characters.
- Both fields require non-blank text. Surrounding whitespace is trimmed before the lengths are checked and the value is saved.
- Manual entry, editing, JSON import and the API enforce these limits without truncating values. Unicode code points count as characters, consistently in the frontend and backend.
- `Width`, `Length`, `Depth` (mm) and `Weight` (kg) must be greater than zero. `Quantity` is at least 1. `BoxGroup` is optional.
- An item's weight cannot exceed the largest payload of the available active boxes. See [Database](database.md#item-weight-limit). The current limit is returned by `GET /orders/item-weight-limit`.
- `POST /boxes/import` rejects duplicate `Reference` values and applies the reviewed result as one transaction. See [Database](database.md#box-inventory-quantities) for quantity rules.
- A new account password must be at least 8 characters.

## FitVisualiser Handoff

FitVisualiser cannot attach the Portal bearer token when it fetches a URL, so the Portal issues a scoped token. Route, environment variable and interface names use the spelling "visualizer".

1. `POST /orders/{id}/visualizer-handoff` (bearer token) returns `SolutionUrl` and `ExpiresIn` (seconds).
2. FitVisualiser requests `SolutionUrl`, which is `GET /orders/{id}/solution/visualizer?token=...`.
3. The token is bound to the order and the exact saved solution. It expires after 300 seconds by default and returns `401` if invalid, expired or issued for a different order or solution.

The base of `SolutionUrl` comes from `PORTAL_PUBLIC_API_URL`. See [Architecture](architecture.md#fitvisualiser-integration).

The `/orders/{id}/solution` response is the unmodified Solver document, with masses in grams. `/orders/{id}/solution/summary` reports kilograms and, for active unfinalised orders, an `InventoryFeasibility` assessment of whether current stock covers the solution.

## CORS

The API allows `DELETE`, `GET`, `POST` and `PUT` with the `authorization` and `content-type` headers. By default it accepts the local Portal (`5174`) and FitVisualiser (`5173`) origins. Set `FITPORTAL_CORS_ORIGINS` to override them.
